The suite's expected timeout/outage log lines are injected failure scenarios, not unexplained failures of the test run. Notification delivery retains an at-least-once crash window if the provider accepts a message immediately before local receipt persistence fails; normal completed-job and active-incident deduplication does not eliminate that transport ambiguity.

## Remaining deployment acceptance

Follow the concrete procedure in [DEPLOYMENT.md](DEPLOYMENT.md) after selecting the host and configuring secrets privately. Before marking the system deployed, capture the deployed revision/package hash, two scheduled cycles on that host with the full enabled-source configuration, stable persistent state after a runtime restart, a received test notification, a controlled persistent-failure incident and recovery, and an independent monitor alert after actually stopping heartbeats. Verify backup restoration and volume/file permissions on that host. A local mock, accepted HTTP request, prepared YAML file, or manual collection does not substitute for those acceptance results.

No paid hosting has been purchased. No passwords or webhook tokens are needed in chat. The prepared commands, secret variable names, budget estimate, and inspection/export process are in [DEPLOYMENT.md](DEPLOYMENT.md) and [OPERATIONS.md](OPERATIONS.md).
