# Hosting, operating cost, and recovery

Prices were checked on **2026-09-19** against the providers' own pages. No account, paid resource, backup bucket, monitor, or Windows scheduled task was created by this preparation. The final machine choice must use the full-source resource measurements and target-host acceptance results, not the size of the original script.

## Measurement-based selection

The early one-source daemon/restart smoke is documented in [VALIDATION.md](VALIDATION.md). It proves local scheduling and persistence, not sizing for 52 sources. The full-source benchmark must record per-cycle elapsed time, process peak resident/private memory, CPU time, source counts/failures, database/WAL size, observations/link-check growth, and notification backlog across at least three five-minute cycles. Include initial import and backup/restore peaks before committing to a very small VM.

Selection rule: first consider the already-always-on PC at $0 hosting cost if its availability is acceptable. For cloud operation, choose the cheapest available plan whose **combined OS, worker, SQLite/cache, and backup peak** stays comfortably below RAM and whose sustained disk/history growth leaves room for WAL, restore staging, and updates. A short Windows sample is not a Linux VM benchmark or a forecast of month-long history growth. Use one writer and a persistent local filesystem; maintain an external monitor regardless of host.

The first full-source local measurement is recorded in `work/acceptance/measurements.json`: at **07:38:04–07:40:42 UTC**, all 52 sources succeeded, elapsed time was **158.6 seconds**, CPU time **71.3 seconds**, and worker peak RSS **157.3 MiB**. The database was **83.44 MB**, with 2,726 retained records. This is a real Windows worker cycle with 25 destination checks and export, not a Linux/container sizing result. The remaining scheduled cycles are separate acceptance evidence.

An actual encrypted **local** restic 0.19.1 backup/restore/check/retention run against that 83.44 MB database completed in **6.063 seconds**, with **5.141 seconds sampled process-tree CPU** and **101.98 MiB peak combined RSS** for the Python helper plus its restic child. Adding the separately measured worker and backup peaks gives about **259.3 MiB**, before the OS, filesystem caches and other services. This is a conservative sum of separate process peaks, not a measured concurrent peak. The local repository avoids network latency and does not establish S3/backend memory, off-host throughput, or alert delivery. Evidence is `work/backup-resource-evidence.json`.

Based on that observed worker footprint, **DigitalOcean's 1 GiB / $6 Basic plan is the lowest-priced cloud candidate recommended among the verified offers above**. The $4/512 MiB plan is not recommended without evidence that the OS and backup/restore peaks fit comfortably alongside the worker. Existing-PC operation remains the cheapest service bill when its availability is acceptable. Recheck memory and a complete source cycle immediately on the selected host; resize if there is swapping, OOM termination, or unacceptable cycle delay. Polling remains a target, with independent source publication and access delays. No monthly database-growth projection is justified by one short cycle.

## Monitoring and backup charges

Healthchecks.io's free Hobbyist plan supports **20 checks**, enough for separate scraper and backup heartbeats. Its 100 log entries per check are a short operational window at five-minute frequency, not a durable audit log; SQLite and local logs retain the worker history. Configure email as the independent alert path in addition to Discord. [Healthchecks pricing](https://healthchecks.io/pricing/)

Backblaze B2 currently includes the first **10 GB** of stored data free, then advertises **$6.95/TB/month** with free API calls. Downloads up to three times average stored data are free; additional downloads are $0.01/GB. For example, 20 GB average stored data is approximately **$0.07/month** beyond the free allowance, before tax/egress. This is an estimate of stored encrypted backup data, not the live database file alone. [B2 pricing](https://www.backblaze.com/cloud-storage/pricing)

Daily full restore verification can exceed B2's free egress allowance even when stored data is small, because restic deduplicates retained backups. Thirty daily restores of a 0.1 GB database transfer roughly 3 GB; at $0.01/GB the all-paid upper bound is $0.03 before its free allowance. At 1 GB per daily restore that upper bound is $0.30. Compression and actual repository size change the bill. Set [B2 billing caps/alerts](https://www.backblaze.com/docs/en/cloud-storage-data-caps-and-alerts) and keep a small backup budget allowance rather than promising zero cost forever.

Thus a 1 GiB DigitalOcean candidate is approximately **$6/month plus tax and measured backup overage**, or **$7.20/month plus those extras** if optional weekly provider images are also selected. Existing-PC operation can stay near $0 service charges within the free tiers, but does not make electricity or availability free. At an illustrative incremental 20 W and $0.20/kWh, 24-hour operation adds about $2.88 per 30-day month; measure the PC's incremental draw and use the user's actual electricity rate.

## Prepared encrypted backup process

`deploy/backup.py` makes a SQLite online backup, verifies integrity and per-table content hashes, and saves a manifest plus non-secret JSON configuration. Off-host mode uploads these stable files using restic, restores the acknowledged snapshot to a temporary directory, verifies its database against the manifest, checks repository metadata, then applies retention and signals success. Only after verification can the backup heartbeat turn healthy. A separate `/fail` signal and missing-success deadline cover failure or a stopped backup task.

Restic snapshots are encrypted with the repository password. Store that password in a password manager separately from the host; losing it prevents restoration. Keep the access key bucket-scoped. Use B2's **S3-compatible API**, as currently recommended by restic because of native B2 backend error handling; choose the actual bucket region endpoint. For the dedicated bucket, use B2's keep-last-version lifecycle so hidden object versions do not defeat restic pruning. Do not add an expiration rule that deletes still-referenced restic objects. [Restic repository setup](https://restic.readthedocs.io/en/stable/030_preparing_a_new_repo.html)

The supplied policy retains **7 daily, 4 weekly, and 6 monthly snapshots** tagged `internship-watch`, grouped by host and paths. Retention deliberately deletes older eligible snapshots after successful restore verification. A host/path migration creates another group; inspect it before deleting the previous host's last recoverable copy. [Restic retention](https://restic.readthedocs.io/en/stable/060_forget.html)

The local copy and restore verifier passed against the early smoke database (84 jobs and all 11 tables; `work/backup-local-test/last-success.json`). A later encrypted local restic repository test passed on the 83.44 MB database with 2,726 jobs and all 12 application tables: backup, restored-data comparison, repository check, retention, and rejection of a wrong encryption password. The official release checksum was verified before execution. A separate local retention drill created 11 snapshots with synthetic historical dates; the supplied policy removed four, retained seven including the newest, passed `restic check --read-data`, and restored the retained database successfully (`work/backup-retention-evidence.json`). Off-host upload/restore, automatic scheduling, the Docker backup path, and real backup alerts still require target-host/provider acceptance. A live `.sqlite3` file alone must not be copied while ignoring WAL; the supplied process uses SQLite's backup API first.

## Windows startup option

`deploy/register-windows-task.ps1` prepares a task without storing a user password. Its default runs at the current user's logon with an interactive token; it stops being dependable when that user logs off and will not cover a reboot before login. Its `-AtStartup` mode uses the passwordless **Local Service** account and needs administrator setup, a machine-wide Python installation, and explicit access to the repository, state and private environment file. The script rejects a virtual environment whose base Python lives in the installing user's profile. [Microsoft task security contexts](https://learn.microsoft.com/en-us/windows/win32/taskschd/security-contexts-for-running-tasks)

`deploy/windows_runner.py` loads only the supported secret variables from a private `.env`, runs the worker/backup child hidden, and rotates local logs. The Task Scheduler settings reject overlaps and restart failed tasks. Neither script changes sleep policy, registers or starts a task merely by being present, or guarantees home-network availability. Test lock-screen, logout if applicable, reboot, sleep/resume, and monitor expiry after choosing this PC. See [CONNECTIONS.md](CONNECTIONS.md) for exact setup steps.
