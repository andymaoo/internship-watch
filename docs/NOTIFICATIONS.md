# Notification policy

Posting validity and application access are separate recorded facts. `posting_status` and `application_status` are each `open`, `closed`, or `unverified`; the older `status` field remains the conservative combined result. A timeout, rate limit, access restriction, or missing evidence does not prove a posting is closed.

| Stored match | Notification behavior |
| --- | --- |
| New, included, posting open, application open | Immediate new-job alert after the collection/check cycle |
| New, included, posting open, application unverified | Immediate alert explicitly labeling application access **UNVERIFIED** |
| New, included, posting unverified | Separate **Unverified internship digest — needs review** |
| New, included, posting open, application closed | Same review digest; hold the immediate alert and recheck |
| Posting closed, excluded, or eligibility ambiguous | No new-job alert or unverified-match digest |
| Existing baseline | One grouped initial backlog report when `initial_run` is `digest`; no individual backlog alerts |

The initial report includes category counts, posting/access totals, and verified postings first. It is one bounded message, with the full list available in the private export. Each newly enabled source imports its existing records as baseline; the initial-report key is global and is not recreated for each source. `initial_run: "silent"` suppresses the initial report.

`awaiting_digest_seconds` controls the minimum spacing between new unverified digest batches (default 900 seconds). The first batch may send immediately. Only previously unreported new matches enter a batch. Membership persists in `digest_jobs` independently from immediate alert receipts: receiving an unverified digest does not suppress a later verified-posting alert. Pending digests are rebuilt before sending to remove excluded, closed, or newly verified members. Empty batches are cancelled. Messages summarize large batches and direct the reader to the full private export.

`poll_seconds: 300` targets a five-minute collection cadence. Source delays, timeouts, service downtime, and the bounded validation queue can extend discovery or alert latency. Each run records source, validation, delivery, export, and total timing; outstanding validation count/age; pending messages; and first-discovery-to-qualification/decision measurements. Older imported records may have unknown qualification history. The validator rotates between fresh new jobs, unchecked baseline records, and due rechecks, and persists the next group across restarts. New listings do not wait behind the entire imported backlog; each active group gets turns, and spare turns go to groups that have work.

First unresolved checks and transient failures normally retry after `unverified_recheck_seconds` (3600 seconds). Two consecutive checks showing the same stable access/content problem use `blocked_recheck_seconds` (21600 seconds): examples include explicit robots denial, login requirements, repeated 403 responses, identity mismatch, and missing meaningful descriptions or application forms. Timeouts, 429/5xx responses, unavailable robots policies, and active host cooldowns retain the shorter schedule. A changed title or destination invalidates old checks and enters the fresh queue immediately. This backoff never changes an unverified record to closed. The chosen delay and reason are saved with each check and counted in each run summary. No validation-history pruning is enabled.

The first measured live cycle checked 25 records within its 60-second validation budget, collected all 52 sources in about 86 seconds, and completed in about 158 seconds. That single sample implies roughly 300 validations per hour at a five-minute cadence, not a guaranteed sustained rate. Rechecking 1,000 stable blocked listings hourly would exceed that capacity; a six-hour interval reduces their average demand to about 167 checks per hour after the initial confirmation checks. When all three queue groups remain busy, approximately one third of validation turns go to each; 1,000 unchecked baseline records could therefore take roughly ten hours at that sample rate. Faster responses and unused turns shorten that time; slow sources or more new jobs extend it. There is no finite worst-case discovery or alert guarantee during source outages, access blocks, provider downtime, or an input backlog that continually exceeds service capacity. Source publication/feed delays precede the recorded first-seen time and must be added separately.

Notifications are committed to SQLite before delivery. Successful provider acknowledgments store their receipt ID; completed job/incident keys suppress routine duplicates. Failed sends remain queued with bounded exponential backoff. Provider rate limits persist a delivery cooldown. Discord delivery is **at least once**, not exactly once: if Discord saves a message but its acknowledgment is lost, or the process stops before committing the receipt, a retry can duplicate that message.

Persistent source, empty-result, and delivery failures create deduplicated operational incidents. Recovery is sent only for an incident whose failure alert was delivered; a renewed outage cancels a stale pending recovery message. An independent heartbeat service must monitor the worker and use its own alert route so it can report a stopped scraper or broken notification provider.

Use `python -m internship_watch --config config.json --env-file private.env drain` to retry due messages without collection. Keep the environment file private; supported notification secrets are documented in the example environment configuration. Inspect SQLite `outbox`, `digest_jobs`, `incidents`, and `runs` or use the `status` command. `export_directory` refreshes the local HTML, CSV, JSON, and link evidence after each completed pipeline run; publish it only through an explicitly configured private access path.
