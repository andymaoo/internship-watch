## Scope and original flow

All ten tracked, project-owned files were inspected: `scrape.py`, `apple_scraper.py`, `google_scraper.py`, `meta_scraper.py`, `requirements.txt`, `README.md`, `CHANGELOG.md`, `seen.json`, `.github/workflows/scrape.yml`, and `.github/workflows/.gitignore`. The state file is JSON data, with 5,472 unique historic IDs and no delivery ledger. No repository AGENTS.md or test suite was present. The requirements file contained only an unpinned `requests` dependency. The README contained only the project title.

The original Actions workflow starts on a ten-minute cron or manual dispatch, checks out `main`, installs requests, and calls `scrape.py`. `main()` reads `seen.json`, loops over a hardcoded company registry, fetches each source, runs a title substring filter, and creates new-job notifications by subtracting historic IDs. The first run is silent. Subsequent runs POST jobs and some scraper errors to ntfy. It then unions every currently collected ID into `seen.json`, whether a notification was acknowledged or not. Actions commits that file, rebases on `main`, and pushes. There is no job database, persistent source health, delivery queue, expiry validation, independent heartbeat or overlap lock.

Useful foundations are the small Python runtime, structured ATS integrations, source isolation by exception handling, the existing Simplify feed adapter, and the accumulated employer registry. Replacing these with a browser automation stack would increase session/token/schema maintenance. Keep those working pieces; replace the orchestration, classification, state and notification contracts that cannot meet the reliability requirements.

## Selected architecture and sequence

Python + requests + SQLite remains the appropriate foundation for one user's collector. The code now separates sources, classification, link verification, persistence, delivery and the CLI. It avoids a queue server, browser farm and public dashboard. Deploy one process on a Linux host, keep SQLite on durable local storage, export HTML/CSV/JSON privately, and monitor it from a separately hosted dead-man service. This is simpler to maintain than distributed workers at the measured scale. A future multi-user/multi-writer service would warrant PostgreSQL and a dedicated worker queue.

The implementation establishes baseline reproductions; proves one complete source-storage-delivery path; enables verified source migrations/expansion; checks live destinations; then prepares deployment and acceptance evidence. Focused tests cover all requested role families, PM, hardware boundaries, US/remote/junior/program eligibility, pagination, cross-source duplicates, delivery failures and starvation, source outages, empty results, expiry, schema drift, restart recovery and locks. Delivery provider tests use acknowledged mocks; they are not real user notification receipts.

The user-selected target is five-minute polling. Direct boards are polled at that target; link validation has both a count and time budget so a large initial import does not monopolize a cycle. Initial backlog and inaccessible pages may delay or prevent a notification. HTTP/DNS operations cannot promise hard wall-clock deadlines on every platform. No overlapping cycles are started. Public Simplify curation and daily export add independent delays, so a five-minute loop cannot guarantee five-minute employer-to-alert freshness.

Persistent fields include employer/title/category/location, description and employment/eligibility evidence, source IDs and original records, original/final description/application URLs, status and validation evidence, first/last seen and last checked, employer date only when supplied, source health, run history and a separate outbox. Historical observations are recorded only on changes. `seen.json` stays unchanged; explicit migration suppresses old IDs without claiming that they were delivered.

Default first-run behavior is silent. Optional digest is one aggregated initial summary with verified examples and explicit unresolved counts, not one notification per imported job. New alerts require included classification and verified destinations. An incident is suppressed until recovery; failed notifications persist across restarts. Provider acceptance followed by process failure can still cause a duplicate retry; no exactly-once guarantee is made.

## Deployment boundary

The production recommendation is an existing always-on Linux host at $0 incremental compute, or a small paid host around $6–10/month with backups. The representative priced option and external monitor are documented with primary sources in [RESEARCH.md](RESEARCH.md). Free GitHub Actions schedules can be delayed/dropped and do not supply this service's persistent disk or five-minute guarantees; they are not the selected production foundation. No account or paid service has been created.

[DEPLOYMENT.md](DEPLOYMENT.md) and [OPERATIONS.md](OPERATIONS.md) provide systemd/Docker configuration, secret setup, commands, backup/restore, rollout and exact acceptance checks. Target-host scheduled runs, state persistence through a target-host restart, a real delivered test notification, a real failure alert and a stopped-worker heartbeat alert remain mandatory before describing this as deployed. The final delivery report distinguishes local evidence from these outstanding access-dependent checks.
